# 常见问题排查

本文档收录 PGI 系统启动、运行、AI 功能、性能四类高频问题及排查方案。遇到问题先看这里，90% 的常见报错都能快速定位。

## 一、启动类问题

### Q1：`Access denied for user 'root'@'localhost'`

**原因**：MySQL 密码不对

**解决**：
1. 检查 `ruoyi-admin/src/main/resources/application-druid.yml`
2. 将 `password` 改为你本地的真实 MySQL 密码

```yaml
spring:
  datasource:
    druid:
      master:
        url: jdbc:mysql://localhost:3306/pgi?...
        username: root
        password: 你的真实密码
```

**排查步骤**：
- 命令行测试连接：`mysql -u root -p`
- 确认密码是否包含特殊字符（需要 YAML 转义）

---

### Q2：`Redis connection refused`

**原因**：Redis 未启动

**解决**：
- 检查 Redis 服务是否运行（默认 6379 端口）
- 命令行测试：`redis-cli ping`（返回 PONG 即正常）
- 如果本机没装 Redis，建议用 Docker：
  ```bash
  docker run -d -p 6379:6379 --name redis redis:7-alpine --requirepass 你的密码
  ```
- 检查 `application.yml` 中 Redis 密码是否与本地一致

```yaml
spring:
  data:
    redis:
      host: localhost
      port: 6379
      database: 4
      password: 你的密码    # 无密码则置空
```

---

### Q3：`ChromaDB connection refused`

**原因**：ChromaDB 未启动，但 `include: ai` 已开启

**解决**（二选一）：

**A. 启动 ChromaDB**
```bash
docker run -d -p 8000:8000 --name chromadb chromadb/chroma:latest
curl http://localhost:8000/api/v1/health  # 验证返回 heartbeat
```

**B. 暂时跳过 AI 模块**
```yaml
# application.yml
spring:
  profiles:
    active: druid
    # include: ai    # 注释掉
```

---

### Q4：`Java: invalid source release: 21`

**原因**：IDEA 的 JDK 未设置为 21

**解决**：
1. `File → Project Structure → Project SDK → 选择 JDK 21`
2. `File → Settings → Build → Compiler → Java Compiler → 设置为 21`
3. 确认 `pom.xml` 中 `java.version` 为 21

---

### Q5：前端页面空白或接口报 500

**原因**：后端未启动或启动失败

**解决**：
1. 查看 IDEA 控制台后端日志是否有报错
2. 确认后端已成功监听 8080 端口
3. 浏览器直接访问 `http://localhost:8080` 验证
4. 前端 Vite 代理配置：`vite.config.js` 中 `/dev-api` → `http://localhost:8080`
5. 如修改了后端端口，需同步改 `vite.config.js` 中的 `baseUrl`

---

### Q6：Maven 依赖下载失败

**原因**：网络问题或 Maven 仓库不可达

**解决**：
1. 配置阿里云镜像（`~/.m2/settings.xml`）：
```xml
<mirror>
    <id>aliyunmaven</id>
    <mirrorOf>*</mirrorOf>
    <url>https://maven.aliyun.com/repository/public</url>
</mirror>
```
2. 删除本地仓库缓存重试：`rm -rf ~/.m2/repository/org/springframework`
3. IDEA 中 `Reload Maven Project`

## 二、运行类问题

### Q7：AI 对话无响应

**排查步骤**：
1. 确认 `application-ai.yml` 中 `api-key` 已配置真实 DeepSeek Key
2. 确认 ChromaDB 已启动（即使不用 RAG 也需启动，因为 Spring AI 自动配置会连接）
3. 检查网络能否访问 `https://api.deepseek.com`
4. 查看后端日志是否有 `AiModelTimeoutException`
5. 检查浏览器控制台 SSE 连接是否建立

```yaml
spring:
  ai:
    openai:
      base-url: https://api.deepseek.com
      api-key: sk-你的真实key
```

---

### Q8：状态流转失败，提示"非法状态跳转"

**原因**：违反[[状态机设计|状态机]]规则

**解决**：
- 查看报错的 `errorCode` 和错误信息
- 对照[[业务规则体系|业务规则]]确认前置条件是否满足
- 例如：`BIZ-008 投标不足 3 家，不可开标` → 需先有≥3 家投标
- 例如：`BIZ-046 评标专家不少于 3 人且为奇数` → 补充专家

---

### Q9：文件上传失败

**排查**：
1. 检查文件大小（≤100MB，BR081）
2. 检查文件类型是否在白名单内（BR082）
3. 检查 `application.yml` 中 `ruoyi.profile` 上传路径是否有写权限
4. 重复上传同一文件会触发 MD5 去重（正常行为，非报错）

```yaml
ruoyi:
  profile: D:/ruoyi/uploadPath    # 确保有写权限
```

---

### Q10：数据权限失效，看到不该看的数据

**原因**：`@DataScope` 注解未生效

**解决**：
1. 确认 Service 方法加了 `@DataScope(deptAlias="d")`
2. 确认 Mapper XML 中 SQL 别名 `d` 对应 dept 表
3. 确认当前用户已分配正确的部门（`sys_user.dept_id`）
4. 确认角色的数据权限范围配置正确

---

### Q11：乐观锁失败，提示"数据已被修改"

**原因**：并发更新冲突

**解决**：
1. 刷新页面获取最新数据
2. 重新提交操作
3. 这是正常的并发控制机制，防止覆盖他人修改

```sql
-- 后端执行的 SQL
UPDATE pgi_project
SET status = #{status}, version = version + 1
WHERE id = #{id} AND version = #{version}
-- 如果 version 不匹配（被别人改过），影响行数为 0，抛异常
```

## 三、AI 功能类问题

### Q12：RAG 检索结果不准确

**优化方向**：

| 优化方向 | 方法 |
|---------|------|
| 分块参数 | 调整 `chunk_size`（默认 500）和 `overlap`（默认 50） |
| Top-K | 调整检索数量（默认 5） |
| 文档质量 | 确保上传的文档结构清晰、内容完整 |
| 向量化模型 | 当前用智谱 embedding-2（1024 维），中文效果好 |

```yaml
rag:
  chunk:
    size: 500       # 调大可减少分块数，调小可提高精度
    overlap: 50     # 调大可提高上下文连续性
  retrieval:
    top-k: 5        # 调大可召回更多结果
```

---

### Q13：AI 工具调用不触发

**排查**：
1. 确认工具类加了 `@Component` 和 `@Tool` 注解
2. 确认 `ToolRegistry` 启动时扫描到工具
3. 确认当前用户有对应权限（`SecurityUtils.checkPermi`）
4. 查看工具调用日志表 `pgi_ai_tool_call_log`
5. 检查工具的 `@Tool(description=...)` 描述是否清晰，AI 才能准确识别意图

---

### Q14：AI 写操作卡住不执行

**原因**：写操作需用户确认（[[工具调用体系|安全机制]]）

**解决**：
1. 检查前端是否弹出确认框
2. 检查 `pgi_ai_action_record` 表 `confirm_status` 是否为 '0'
3. 调用 `/api/ai/action/confirm/{id}` 确认执行
4. 如需撤销，调用 `/api/ai/action/rollback/{id}`

---

### Q15：AI 用量成本异常高

**排查**：
1. 查询 `pgi_ai_usage_log` 表统计 token 消耗
2. 检查是否有长上下文导致 input token 暴增
3. 调整 `max-tokens` 限制（默认 4096）
4. 检查短期记忆窗口（默认 20 轮，过长会增加 token）

```sql
-- 查询某用户用量
SELECT DATE(call_time), SUM(token_input), SUM(token_output), SUM(cost_amount)
FROM pgi_ai_usage_log
WHERE user_id = #{userId}
GROUP BY DATE(call_time)
ORDER BY DATE(call_time) DESC;
```

```yaml
spring:
  ai:
    openai:
      chat:
        options:
          max-tokens: 4096    # 限制输出 token
          temperature: 0.7
```

---

### Q16：向量化任务失败

**排查**：
1. 查询 `pgi_ai_embedding_job` 表 `status` 和 `error_msg`
2. 检查 `retry_count` 是否已达上限（3 次）
3. 检查智谱 API Key 是否有效
4. 检查文档是否能被 Tika 解析（PDF/Word/MD/TXT）

```sql
SELECT * FROM pgi_ai_embedding_job
WHERE status = 'FAILED'
ORDER BY update_time DESC;
```

## 四、性能类问题

### Q17：SSE 流式对话卡顿

**优化**：
1. Nginx 配置 `proxy_buffering off`（生产环境必须）
2. 检查心跳间隔（15 秒）
3. 单用户单连接，避免多连接资源泄漏
4. 后端 `SseEmitter` 超时设为 3600 秒
5. 检查网络延迟

```nginx
location /prod-api/ {
    proxy_pass http://app:8080/;
    proxy_buffering off;        # SSE 必须关闭缓冲
    proxy_cache off;
    proxy_read_timeout 3600s;   # 超时时间
}
```

---

### Q18：定时任务集群环境重复执行

**原因**：多实例同时执行 `@Scheduled` 任务

**解决**：
- 任务执行前加分布式锁（Redisson）
- 只有抢到锁的实例执行，其余跳过

```java
@Scheduled(fixedRate = 60000)
public void processJobs() {
    RLock lock = redissonClient.getLock("embedding_job_lock");
    try {
        if (lock.tryLock(0, 60, TimeUnit.SECONDS)) {
            // 执行任务
        }
    } finally {
        if (lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
}
```

---

### Q19：数据库查询慢

**排查**：
1. 启用 Druid SQL 监控面板（`/druid`）
2. 检查慢 SQL 日志
3. 确认查询是否加了 `del_flag = '0'` 索引
4. 确认分页是否用了 PageHelper
5. 检查是否缺少必要索引

---

### Q20：内存占用过高

**排查**：
1. 查看服务监控（`/monitor/server`）
2. 检查 SSE 连接是否泄漏（单用户单连接）
3. 检查长期记忆是否堆积（`MemoryDecayScheduler` 是否执行）
4. 调整 JVM 参数：`-Xmx2g -Xms2g`

---

## 五、部署类问题

### Q21：Docker 容器启动失败

**排查**：
1. `docker logs <容器名>` 查看日志
2. 确认依赖服务（mysql/redis/chroma）已启动
3. 检查端口是否冲突
4. 检查环境变量是否注入

---

### Q22：Docker Compose 服务启动顺序

`docker-compose.yml` 中通过 `depends_on` 定义依赖：

```yaml
services:
  app:
    depends_on:
      - mysql
      - redis
      - chroma
```

但 `depends_on` 只保证启动顺序，不保证服务就绪。建议：
- 应用层加重试机制（Spring Boot 自动重试连接）
- 或用 `wait-for-it.sh` 脚本等待服务就绪
