# 项目创建过程

本文档完整记录 PGI 招标智能 AI 管理系统从构思到落地的全过程，包括业务背景、关键里程碑、技术决策节点、踩过的坑和突破方案，以及后续迭代规划。供客户、新成员和评审者快速理解项目"为什么做、怎么做、做到哪一步"。

## 一、项目构思背景

### 1.1 招标业务的四大先天痛点

招标业务天然具备 **流程长、角色多、规则严、文档杂** 四大特征，这四个特征叠加在一起，使得传统招标管理软件长期停留在"流程线上化"层面，无法真正解决从业者的痛点。

| 特征 | 具体表现 | 带来的问题 |
|------|---------|-----------|
| **流程长** | 一个招标项目从立项到归档要经过立项→公告→投标→评标→中标→归档 6 个主阶段，每阶段又有若干子环节 | 用户需要在多个菜单间反复跳转，操作链路长、效率低 |
| **角色多** | 涉及代理机构、招标人、投标方、审核人员、评标专家、评标组长等 5+ 类角色 | 协作成本高，权限管理复杂，数据易串库 |
| **规则严** | 受《招标投标法》《政府采购法》等法规约束，有大量硬性规则（公示期不少于 3 天、评标专家不少于 3 人且为奇数、报价不得超预算等） | 规则散落在文档和口头经验中，靠人记容易漏，一旦违规可能引发投诉甚至诉讼 |
| **文档杂** | 招标文件、投标文件、资质证书、评标报告、合同等文档量大、格式多样 | 检索困难，历史标书无法复用，新人上手慢 |

### 1.2 传统招标系统的局限

市面上的招标管理系统大多解决的是"流程线上化"问题，即把纸质流程搬到线上，但并没有解决 **智能化** 问题：

- 用户仍需逐个点击菜单完成操作，没有自然语言交互能力
- 招标法规、企业制度等文档堆积在文件服务器里，只能按文件名查找，无法语义检索
- 业务规则靠开发时硬编码或人工记忆，规则变更需要改代码，响应慢
- 状态字段被人工直接修改，流程容易卡死或跳步
- 缺乏 AI 辅助，撰写公告、整理评标报告等仍需人工逐字敲

### 1.3 AI 时代的机遇

随着大语言模型（LLM）和 RAG（检索增强生成）技术的成熟，"让 AI 真正介入业务操作"成为可能。但市面上的 AI 招标方案大多停留在"接个聊天机器人"的层面，AI 只能聊天，不能动手操作业务，更没有安全审计机制——这让企业不敢真正用 AI 处理招标这种高合规要求的业务。

本项目的定位是：**做一个 AI Native 的招标全流程管理平台**，让 AI 不只是聊天助手，而是能通过工具调用真正"动手"操作业务（查项目、检索文档、代为提交操作），同时用状态机 + 规则引擎 + 幂等机制 + 审计回滚把安全做到法规级，让企业敢用、能用、放心用。

## 二、项目立项与目标

### 2.1 项目正式名称

**魔丸组超级工程招标智能 AI 前沿信息管理系统**（简称 PGI 系统）

### 2.2 核心目标

| 目标层 | 具体内容 |
|--------|---------|
| **业务目标** | 覆盖招标全生命周期（项目→公告→投标→评标→中标→归档），支持多角色协作，满足招投标法规合规要求 |
| **AI 目标** | AI 智能体可通过自然语言对话调用 12 个业务工具，RAG 知识库基于企业文档回答问题，写操作可确认可回滚 |

### 2.3 项目边界

**包含**：
- 招标全流程业务（M02-M12）
- AI 智能体（M13，含对话/工具/记忆/用量审计）
- RAG 知识库（M14，含文档解析/分块/向量化/检索）

**不包含**（已决策移除）：
- AI 资讯爬虫模块（原 M13-news，已从 pom/目录/依赖中清理，聚焦核心招标 + AI 能力）
- 短信通知（仅保留站内信 + 邮件）
- 在线支付（保证金仅记录台账，不接入支付网关）

| 基础框架 | 自研 / RuoYi v3.9.2 / JeecgBoot | RuoYi v3.9.2 二次开发 | 企业级成熟脚手架，省去用户/角色/权限/菜单/字典等基础建设，社区资料丰富 |

| 大模型 | OpenAI GPT-4 / 通义千问 / DeepSeek | DeepSeek（OpenAI 兼容） | 高性价比，中文效果好，通过 OpenAI 兼容接口接入，切换模型成本极低 |
| 向量库 | Milvus / Pinecone / ChromaDB / Weaviate | ChromaDB 1.5.9 | 轻量级，Spring AI 原生支持，单机部署友好，`initialize-schema: true` 自动建集合 |
| Embedding 模型 | OpenAI text-embedding-ada-002 / 智谱 embedding-2 / BGE | 智谱 embedding-2（1024 维） | 中文向量化效果好，OpenAI 兼容接口，成本低于 OpenAI |
| ORM | MyBatis-Plus / 原生 MyBatis + PageHelper | 原生 MyBatis + PageHelper 4.0.1 | SQL 透明可控，符合招标业务对数据精确性的要求，乐观锁/逻辑删除手动写更清晰 |
| 前端框架 | Vue 2 / Vue 3 / React | Vue 3 + Vite + Element Plus | 现代技术栈，组合式 API，Vite 极速 HMR，Element Plus 企业级组件 |

#### 关键决策：双端点解耦

这是技术选型中最关键也最棘手的决策。规范 11.4 章节锁定了对话模型用 DeepSeek、向量化模型用智谱 embedding-2，二者分属不同端点：

```
DeepSeek:  https://api.deepseek.com              (chat)
智谱:       https://open.bigmodel.cn/api/paas/v4/ (embedding)
```

但 Spring AI 的 OpenAI starter 中 `base-url` 和 `api-key` 是连接级共享的，同一个 `OpenAiChatModel` 和 `OpenAiEmbeddingModel` 会读取同一组配置。如果直接用自动配置，chat 和 embedding 会指向同一个端点，导致其中一个失败。

**突破方案**：在 `ruoyi-rag/embedding/EmbeddingConfig` 中自定义 `OpenAiEmbeddingModel` Bean，显式指向智谱端点，用 `@Primary` 注解覆盖自动配置，让 `ChromaVectorStore` 注入这个自定义 Bean。chat 仍然走 DeepSeek 的自动配置。

```java
@Configuration
public class EmbeddingConfig {

    @Bean
    @Primary
    public OpenAiEmbeddingModel embeddingModel() {
        OpenAiApi api = OpenAiApi.builder()
            .baseUrl("https://open.bigmodel.cn/api/paas/v4/")
            .apiKey(zhipuApiKey)
            .build();
        return new OpenAiEmbeddingModel(api,
            MetadataMode.EMBED,
            OpenAiEmbeddingOptions.builder().model("embedding-2").build());
    }
}
```

## 四、关键决策节点详解

### 决策 1：模块合并策略

规范定义了 15 个模块（M01-M15），但实际 Maven 模块只建了 9 个。这是工程实用性与规范纯粹性之间的平衡。

**合并方案**：
- M02 project / M03 notice / M04 document → 合并到 `ruoyi-bid`（同属"招标管理"前端菜单分组）
- M05 bid / M06 evaluation / M07 award → 合并到 `ruoyi-bid`（同属"交易管理"）
- M08 qualification / M09 attachment / M10 audit / M11 deposit / M12 venue → 合并到 `ruoyi-bid`
- M13 ai → 独立模块 `ruoyi-ai`
- M14 knowledge → 独立模块 `ruoyi-rag`
- M15 notify → 独立模块 `ruoyi-notify`

**关键约束**：Service 层保持独立（`IProjectService` / `ITenderNoticeService` / `ITenderDocumentService` 各自实现），不影响规范 1.2 节依赖矩阵中的跨模块调用规则。Controller、Service、Mapper、Entity 均位于各自 Maven 模块内，遵循 DC-042 包结构规范 `com.ruoyi.{module}.{controller|service|mapper|entity|dto|vo}`。

### 决策 2：原生 MyBatis 而非 MyBatis-Plus

规范 11.4 锁定使用原生 MyBatis + PageHelper，而非更"省事"的 MyBatis-Plus。理由：

| 维度 | MyBatis-Plus | 原生 MyBatis |
|------|-------------|-------------|
| 乐观锁 | `@Version` 注解自动处理 | XML 手动 `version+1 WHERE version=#{version}` |
| 逻辑删除 | `@TableLogic` 注解自动过滤 | XML 手动 `del_flag='0'` 过滤 |
| 审计字段 | `MetaObjectHandler` 自动填充 | Service 层手动 set |
| SQL 透明度 | 隐式生成，调试难 | XML 显式，SQL 一目了然 |
| 适用场景 | 快速 CRUD 业务 | 对数据精确性要求高的业务 |

招标业务涉及资金（保证金）、合规（公示期）、法律（中标结果），每一条 SQL 都需要可审计、可追溯。原生 MyBatis 让 SQL 完全透明，符合招标业务的严谨性要求。

### 决策 3：资讯模块移除

原设计包含 AI 资讯爬虫模块（ruoyi-news），用于抓取 arXiv / HuggingFace / OpenAI / 机器之心等源的 AI 前沿资讯，并通过 LLM 分类打标、SimHash 去重、按订阅频率推送。

**移除原因**：
- 聚焦核心招标 + AI 能力，避免摊子铺太大
- 资讯爬虫涉及反爬、版权等外部依赖，增加项目不确定性
- 客户核心诉求是招标流程智能化，资讯是锦上添花

**移除操作**：从 pom / 目录 / 依赖中彻底清理，规范文档保留模块定义以备未来恢复。

### 决策 4：事件驱动解耦

招标业务存在两处天然的双向依赖，若不解耦会形成循环依赖导致 Spring 启动失败。

| 双向依赖场景 | 解耦机制 |
|-------------|---------|
| 知识库（M14）↔ AI（M13）| M14 发 `EmbeddingJobEvent`，M13 监听执行向量化 |
| 业务模块 → 通知（M15）| 业务 publish `NotifyEvent`，M15 监听异步发送 |

通过 Spring 的 `ApplicationEventPublisher` + `@EventListener` + `@Async` 实现，既解耦了依赖，又实现了异步处理（通知发送不阻塞业务主流程）。

详见 [[架构设计]]。

## 五、挑战与突破

### 挑战 1：Spring AI 2.0 是较新版本，API 可能与文档示例有差异

**突破方案**：
- 实现时以 Spring AI 2.0.0 官方文档为准，不依赖博客示例
- 先写最小可运行 demo 验证 API（如 ChatClient.prompt().stream() 的返回类型）
- 关键 API（`@Tool` 注解、`Advisor` 接口、`ChatMemory`）逐一验证

### 挑战 2：chat 与 embedding 双端点

详见上文"关键决策：双端点解耦"。

### 挑战 3：SSE 高并发资源泄漏

SseEmitter 在高并发下可能资源泄漏（连接不释放、内存堆积）。

**突破方案**：
- 单用户单连接限制（同一用户同时只有一个 SSE 连接）
- 心跳保活（15 秒发送一次心跳，防止代理超时断开）
- 超时自动关闭（3600 秒无活动自动关闭连接）
- 连接关闭时主动释放资源（`emitter.complete()` / `emitter.completeWithError()`）

### 挑战 4：AI 写操作的安全风险

AI 直接改业务数据，一旦出错（如误删项目、错误修改中标结果）无法追溯——这是企业不敢用 AI 的核心顾虑。

**突破方案**（四重安全机制）：
1. **写操作确认**：写工具（`risk_level='1'或'2'`）执行前创建 `pgi_ai_action_record`，暂停执行，前端弹窗确认
2. **before/after 快照**：确认后执行，记录操作前后的数据快照
3. **一键回滚**：用户可调用 `/api/ai/action/rollback/{id}` 根据 before 快照恢复
4. **全量日志**：工具调用日志 + AI 操作记录 + 用量日志三层审计

详见 [[工具调用体系]]。

### 挑战 5：多人协作文档与代码漂移

多人协作时，文档和代码容易不一致（文档说 A，代码写 B），后期维护成本高。

**突破方案**：SSOT 原则 + 8 条 AI 执行约束（AC-01 ~ AC-08）。文档是唯一事实来源，AI 生成代码前必须读文档，文档与代码冲突时以文档为准，违反约束的代码不予合并。

### 挑战 6：集群环境定时任务重复执行

生产环境多实例部署时，`@Scheduled` 任务会在每个实例都执行，导致状态重复流转、保证金重复退还。

**突破方案**：任务执行前加 Redisson 分布式锁，只有抢到锁的实例执行，其余跳过。
